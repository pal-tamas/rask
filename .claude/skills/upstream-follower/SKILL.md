# upstream-follower

Everything Rask takes from upstream moves the same way, with nobody asked: `upstream.yml` runs each follower
daily as its own job (`upstream-follow.yml`). Each run regenerates, gates what that commit can reach, and lands
it on `main`. Every source keeps ONE issue, opened only when a person is needed and closed by its next green run.
A red that `main` already has is not upstream's: the commit waits on `upstream-waits/<follower>`.

A generated file without a follower goes stale silently. `scripts/tests/upstream-registry.test.sh` fails one
whose header names a generator that is in neither the registry's followers nor its `manual` list.

## The contract (model: `scripts/upstream/cldr.py`)

1. **No argument → the latest stable release**, never a version constant. A follower is Python 3 (stdlib only)
   or a .NET file-based app — never Node: `scripts/tests/no-node.test.sh` and the registry test refuse a
   follower that runs node/npm/npx. An npm package's data: `scripts/upstream/npm.py` (`release`, `tarball`,
   `files`) fetches the registry tarball, refuses it unless it hashes to `dist.integrity`, and reads it in
   memory — nothing is installed, no package script runs. Everything else: `scripts/upstream/upstream.py`
   (`fetch`, `substitute`, `follow`).
2. **The release is written into what it generates**: a header line `Generated by scripts/<x> from <pkg> <version>`,
   or, in JSON, a `_` key with that sentence plus `release` and `integrity`.
3. **`--check`** exits 1 when the committed files are not the latest release's. Unattended, no browser, Python 3
   or .NET. Upstream not answering → exit 0 and change nothing (`follow()` does both).
4. **What it cannot decide is a gate, not a guess.** A rule a person curates, like `PluralRules.cs`, is not
   regenerated. The follower moves a data snapshot, and a test holds the curated code to it
   (`PluralRulesMatchCldrTests`), so the follower's commit fails the gate and its issue opens. Bundle growth
   exits non-zero and never re-records a budget.
5. **New public API** that comes with a release is recorded: `scripts/public-api/record.py <project>` (see `scripts/mdn/follow.sh`).
6. **A self-test over saved answers** in `scripts/tests/upstream-*.test.sh` (`RASK_UPSTREAM_FIXTURES`: a URL with
   no saved answer is an upstream that did not answer). A port of a generator proves byte-identical output by
   running the old and the new one on the same pins and diffing what they write (the MDN refresh did).

## Register it

Add an entry to `scripts/upstream/followers.json`:

```json
{ "name": "cldr-plurals", "kind": "regenerate", "run": "scripts/upstream/cldr-plurals.py",
  "outputs": ["tests/Rask.Generators.Tests/cldr-plurals.json"] }
```

- `kind`:
  - `regenerate`: `follow.sh` runs it, one matrix job each.
  - `measure`: needs a browser, its own job in `upstream.yml` (Flux UI's lock).
  - `match`: writes nothing, only compares (`flux-parity`).
  A `measure` or `match` follower needs an `upstream.yml` job of its own name, and the registry test checks for it.
- `run`: an executable script, `python3 <script>`, or `dotnet run <app.cs>` (the registry test finds the script in each).
- `setup: "dotnet"` when it builds (MDN records the public API from a build of the new snapshot).
- `outputs`: globs. Every one must match a committed file.

That is all: the matrix reads the registry. Something deliberately held (Lucide at 0.300.0, the release whose
boxes match Flux's) goes in `manual` with a `why`. Never make a build refresh anything: a build that writes a
tracked file is how upstream data rode into unrelated commits.

Rask.Ui generators (`scripts/flux`, `src/Rask.Ui`) belong to the `ui` session. Send it the request rather than
editing them.
